# ADR-P2-026: Corpus Trust Boundary (qualify once, verify every run)

**Status:** 🚧 Proposed (2026-11-09) — job 1 implemented; accept with commit B (preflight) <br>
**Phase:** P2


## Decision
Introduce a trust boundary between the source corpus (`data/06_books`) and the offline pipelines, in two jobs:

1. **Qualify once — `qualify_corpus.py` (job 1).** Profiles every chapter deterministically and writes a
   **corpus record** (`data/06_books/corpus_record.json`, DVC-tracked with the chapters it describes).
   A corpus becomes `certified` only after a stratified fidelity sample passes against a reference copy.
2. **Verify every run — preflight (job 2).** Before any API call, the generation pipeline checks the selected
   chapters against the record: the record's status is `certified`, expected files exist, chapter count matches,
   and each chapter's sha256 matches. Any failure stops the run (zero API calls). Recorded character / word counts
   are used only to explain a mismatch (emptied / truncated / edited in place), not to decide it.

**Lifecycle (policy)**
- `profiled` — every chapter measured and fingerprinted; the record pins the exact bytes. Proves presence and
  identity, not correctness. Not usable by the pipeline.
- `certified` — a stratified fidelity sample of each book passed against a reference copy, checked against the
  profiled files. **Required for any pipeline run, trials included** (strict: the corpus is small and defined,
  and the certification process is being established).
- `superseded` — replaced by a newer record (data changed → new `corpus_id` → re-profile; old samples no longer apply).
- QA is performed on the profiled record, never before it: evidence must refer to fixed bytes.
- Profiling refuses to write a record if any check fails (go/no-go), listing every problem in one pass.
- Overwrite rule: a `certified` record whose `corpus_id` is unchanged is left untouched; if the data changed,
  the record is replaced as `profiled` and certification is cleared (the old record stays in DVC history).

**Profiling checks (job 1)**
- Per chapter, cheapest first: file exists → not empty → decodes as UTF-8 → title matches the table of
  contents (only for books whose files carry titles) → record built (sha256 of raw bytes; counts on decoded text).
- Per book: no unexpected files; chapter count equals the table of contents.
- Chapter titles come from an independent **table-of-contents snapshot** (fan-compiled CSV, pinned commit,
  fetched once and committed; joined on book number). The script never calls the network.
- Reviewed title discrepancies are recorded as explicit **title exceptions** (title to record + reason) and
  listed in the profile evidence — deviations are documented, never hidden by loosening the comparison.

**Fidelity pass criterion (job 1, sampling step)**
- **Pass:** the right content in the right chapter; occasional transcription-level typos are acceptable.
- **Fail:** missing, truncated, swapped or garbled passages.

The record is a typed contract (`scripts/corpus/corpus_models.py`) shared by both jobs:
corpus → book (keyed by `Book` enum) → chapter (keyed by 1-based chapter number).

**Corpus record v0.1 (key fields)**
- Corpus: `schema_version` ("0.1", exact match), `corpus_id` (derived: hash of all chapter checksums — changes
  if and only if the data changes), `status` (`profiled` / `certified` / `superseded`), `provenance`
  (source-neutral: `source_type` community / licensed, `origin`, `acquired_from`, extraction script),
  `certification_method` (`manual_review` / `script` / `script+llm`), `date_certified`, `corpus_root`, `scope`
- Book: `expected_chapters` (from the table of contents — an independent reference), `published_year`,
  `isbn` (null until the corpus edition is confirmed), profiling `evidence`, `fidelity_sample` (one per book)
- Chapter: `title` (table of contents, or a reviewed exception), `title_in_text`, `number`, `filename`
  (relative to `corpus_root`), `character_count` (`len()` of decoded UTF-8), `word_count` (`str.split()`),
  `sha256` (raw bytes)
- Invariants (validators): `status = certified` requires a method, a date and a passing fidelity sample for
  every book; chapter dict keys equal `chapter.number`; sampled chapters exist in the book; stored `corpus_id`
  equals the computed one; unknown fields are rejected.


## Options considered
1. **Trust the inputs** (status quo) — the pipeline reads whatever is in `data/06_books`
2. **Run-time content checks only** — length bounds / outlier warnings / title checks on every run, no record
3. **Qualify once + verify by checksum** — a recorded, evidenced baseline; deterministic run-time verification
4. **LLM verification of fidelity** — ask a model to confirm the text matches the book


## Selected option
Option 3 (qualify once + verify by checksum)


## Rationale
- **Prevention upstream beats inspection downstream.** A bad chapter caught before generation costs nothing;
  caught later it has already cost generation, two enrichment passes and validation.
- **Validation cannot catch a wrong corpus.** The validation pipeline checks questions against the same corpus,
  so a corrupted or misaligned chapter would pass validation. The corpus itself needs its own gate.
- **Correctness and integrity are different checks.** A checksum proves *unchanged*, not *correct*: it locks in
  whatever was recorded. Correctness comes from evidence gathered once (job 1); integrity is proven every run
  (job 2). Separating them puts each check where it can catch something.
- **Independent sources are the useful redundancy.** Length and title read from the same bytes as the checksum
  add nothing to the run-time decision (common-cause). Comparing the file's title with an independent table of
  contents does — the first real runs proved it (see Evidence).
- **Option 2 rejected:** legitimate chapters are very short (e.g. Deathly Hallows ch. 37: 1,552 words vs a
  ~5,200 average), so average-based bounds would warn on real chapters every run; and content checks are
  redundant once a checksum matches.
- **Option 4 rejected:** without a reference text, an LLM can only compare against its own memory of the book —
  not evidence, non-deterministic, and liable to recitation blocks. Rigour comes from the reference and the
  sampling plan, not the tool. An LLM may still help with *coherence* (structure, merged chapters, garbled
  text) — see Future considerations.
- **Timing:** the first full book run uses every chapter, most never spot-checked. The baseline must exist
  before it.


## Evidence (first profiling runs, 2026-11-09)
- Run 1: 60 problems. Chapter files are zero-padded (`chapter_01`) — a naming mismatch, fixed in the script;
  the unexpected-file check now compares file names, not numbers.
- Run 2: 41 problems. Book 4 files carry no titles (chapter 1 only) → treated as no titles in text.
- Title check found three discrepancies in book 3, one in each source:
  - ch 8 "FAT FADY", ch 18 "PADDFOOT" — transcription typos in the corpus text (table of contents correct)
  - ch 19 — the table-of-contents snapshot is wrong ("The Servant of the Dark Lord"); the file matches the
    published title "The Servant of Lord Voldemort" (verified online)
  - all three recorded as reviewed title exceptions
- Corpus text also has run-together words across line joins ("fewseconds", "magicto") — a garbled-text defect
  that affects source-quote matching (E2) and is noted for corpus onboarding.
- Final run: passed — 3 books, 96 chapters, `corpus_id 680db04cf48248ce`, status `profiled`.


## Trade-offs
**Pros:**
- Deterministic, millisecond run-time check with one meaning per failure ("not the certified corpus")
- Trust is recorded (evidence, method, date, reviewed exceptions), not remembered in a notebook
- Same gate applies to any future corpus, whatever produced it (qualification is separate from extraction)
- Actionable failures: count diffs explain *how* a chapter changed
- Narrow interface: preflight only reads the status and checksums; how certification is done can change
  without touching preflight

**Cons:**
- Fidelity evidence is partly manual (sampled spot checks against a reference copy)
- Any intended corpus change requires re-qualification before the pipeline runs
- A small contract module and a table-of-contents snapshot to maintain


## Risks
- **Unqualified source.** Text comes from a fan-maintained R package sourced from a book-text site that no
  longer exists; edition unconfirmed. Trust rests on inspection, not supplier qualification.
- **Transcription errors in the body text.** Title typos and run-together words suggest similar errors in the
  body; the pass criterion accepts transcription-level typos but they affect exact quote matching.
- **Sampling, not proof.** A passing stratified sample supports a low defect rate; it does not prove every
  chapter. Mitigated by the 100% deterministic profile and by sampling first/last chapters and short outliers.
- **Books 4 and 7 alignment.** Their files carry no chapter titles, so file-name ↔ content alignment relies on
  the fidelity sample alone — sample more chapters from these books.
- **Fan-compiled table of contents.** Already shown to contain an error (book 3 ch 19); every mismatch is reviewed
  before being recorded as an exception.
- **Self-certification.** One maintainer profiles, samples and approves (no four-eyes review).


## Consequences & Future considerations
**Consequences**
- Package `scripts/corpus/`: `corpus_models.py` (contract), `qualify_corpus.py` (job 1), `preflight.py`
  (job 2, next). Tests in `tests/corpus/`.
- Generation flow calls preflight on the selected chapters before `configure_api` / `measure_template_tokens`.
- Strict status gate: the fidelity sample must be completed before the next pipeline run of any kind; preflight's
  own tests use fake corpora (pytest), so they do not depend on certification. A graded policy (trials accept
  `profiled` with a recorded warning) can be revisited if the corpus grows and certification becomes slower.
- Independent second layer already exists: DVC's own hashes (`dvc status`) detect changed files using
  different software.
- Garbled-text heuristic, LLM structural review and outlier-bound review move to a corpus-onboarding backlog.
- Architecture diagram (design doc, P2 scheme) gains the corpus trust boundary at subsystem level:
  qualification as a one-off step beside the source corpus, preflight as a gate on the edge into generation.
  Updated with commit B, when this ADR is accepted.

**Deferred (captured, add when a consumer needs them — `schema_version` allows additive change)**
- **Certification history:** append-only list of certification events (manual → script → script+LLM);
  current method/date then derived from the latest event. Until then, git/DVC history of the record serves.
- **Record revision:** integer incremented on any record change, so run manifests can cite
  "corpus `<id>`, revision N".
- **Semantic versioning for `schema_version`:** MAJOR.MINOR — preflight refuses an unknown MAJOR, accepts newer
  MINOR. Adopt at 1.0 when the schema stabilises; 0.x exact match until then.
- **Provenance detail:** package / extraction commits; edition, publisher, ISBN confirmation (reference-copy
  ISBN via a one-off library catalogue lookup, saved as a snapshot); UK/US edition family via spelling markers.
- **Passage helper for sampling:** print start / middle / end passages of sampled chapters on demand (never
  stored in the record).
- **Corpus onboarding workflow:** garbled-text heuristic, LLM coherence review (experiment), outlier review,
  for new corpora (e.g. books 1, 2, 5, 6).

**Production / regulated deltas** (proportionate to demo scale and a non-licensed source)
- Production would add a **licensed** source with **supplier-published checksums** or signed artifacts, declared
  data contracts on ingestion, a documented sampling plan, a datasheet / data card, and independent sign-off.
- Regulated settings formalise the same pattern: supplier qualification, data-integrity principles (ALCOA+),
  audit trails, and re-qualification under change control.
- Out of scope for a single-maintainer project: data ownership, access and retention policies.
