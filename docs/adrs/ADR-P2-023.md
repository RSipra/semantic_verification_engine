# ADR-P2-023: DraftQuestion Pydantic model as generation pipeline-spanning source of truth

**Status:** Accepted<br>
**Phase:** Phase 2 (offline question generation pipeline orchestration)

## Decision
Introduce a single `DraftQuestion` Pydantic model as the source of truth for records flowing through the generation pipeline. 

`DraftQuestion` serves as both the schema and the DTO: 
1. *DTO*: modules instantiate it to carry records through the pipeline, populated incrementally by each LLM pass (unfilled fields remain None). It is derived as an all-Optional version of `SyntheticMCQ` (the fullest field set — MCQ inherits Standard plus options) via a factory in models.py, imported as a normal model class and instantiated per record.
2. *API call schema*: Per-pass LLM response schemas are derived from it as field-subsets. This extends the Synthetic (Standard and MCQ) Pydantic models from a validation-only role (tracer design) to spanning generation → enrichment → validation.

*Derivation direction:* the gate model (SyntheticMCQ) defines the field set; Draft is its all-Optional projection. The requirement defines what must be collected.

Question format correctness is enforced at the Bronze gate: each record validates into its type-appropriate Synthetic subclass (Standard vs. MCQ), so Draft's permissiveness carries no downstream risk.

## Options considered
For the LLM schemas:
1. Hand-write each pass schema AND a separate Draft model (manual mirroring).
2. Single Draft model as SOT; derive per-prompt pass schemas as field-subset models (via create_model from DraftQuestion)
3. One all-Optional model used directly as every LLM schema (full field set passed to each call, including later-pass fields); required-ness enforced only at the gate. 

## Selected option
Option 2 (Draft SOT, derived per-pass schemas).

## Rationale
- One place to define fields; avoids drift across passes.
- Keeps strict gate models (SyntheticStandard/MCQ) authoritative and untouched, so tracer-tested downstream (validation pipeline etc) is unaffected.
- Generation and enrichment gain a shared typed contract instead of passing raw dicts.

## Trade-offs
**Pros:** single source of truth; no field mirroring; typed inter-pass contract for each LLM call in the generation pipeline.
**Cons:** dynamically-created models may confuse type checkers (Pylance squiggles on derived-model fields); derivation logic adds a small layer of indirection (the purpose is not directly obvious in module - can refer to ADR in note).

## Risks
- Draft field set and gate (SyntheticStandard) field set must stay in agreement; divergence would surface only at gate-time. Costly with API calls (gate-time failure means the wasted API spend of a full generation run). The factory derivation should keep the sets aligned by construction.
- Some gate fields (generation_prompt_version) come from pipeline metadata, not LLM passes — Draft must account for these too.

## Consequences & Future considerations
- Generation retains JSONL write AND populates DTO list (dual output).
- Enables enrichment passes to consume/return typed List[DraftQuestion] and in-memory pass to the validation pipeline.
- Revisit if field set grows large enough that derivation/type-checker friction outweighs the anti-drift benefit.
- `create_model` copies `model_fields` only. Since `model_config` is a class attribute, and not a field, it does not carry over from the source model. `DraftQuestion` must be given its own config explicitly (`__config__=ConfigDict(use_enum_values=True)`), or enum fields deserialize as enum members rather than values and `model_dump()` output is not directly JSON-serializable. 
    - Note `__config__` and `__base__` are mutually exclusive in `create_model` (cant specify both at the same time; limitation of using `create_model`, not of Pydantic inheritance: a normally-defined subclass can inherit and override `model_config` freely. If the derived model ever needs a base class, define the config on that base and pass it via `__base__`, rather than passing `__config__` separately.).
