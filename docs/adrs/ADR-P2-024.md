# ADR-P2-024: Flat scalar schema fields over nested dicts

**Status:** Accepted (evolving — additional affected fields to be catalogued)<br>
**Phase:** Phase 2 (offline generation pipeline / schema reconciliation)

## Decision
Schema fields use flat scalars and lists of scalars. Dicts used as bags of named fields are flattened into individual columns.

The rule:
- **Lists of primitives** (`List[str]`): keep. Genuinely variable-length data, natively supported by Parquet as `list<string>`.
- **Dicts with a fixed, known key set**: flatten. These are structs pretending to be dicts, and they cost JSON round-trips, unstable type inference, and queryability.
- **Test:** are the keys a fixed, known set? If yes, flatten. If the keys are genuinely open-ended and data-dependent, a dict may be warranted — but first ask whether that data belongs in the record at all.

## Context
`generation_prompt_version` was typed `Optional[Dict[str, str]]`, holding the prompt filename for all three question types:

```python
'generation_prompt_version': {
    'FR': 'fr_master_prompt_v0.1.txt',
    'EX': 'ex_master_prompt_v0.1.txt',
    'MCQ': 'mcq_master_prompt_v1.txt'
}
```

This shape was an artifact of the tracer's workflow: `generation_metadata` was appended in bulk to the whole dataframe *after* all three question types had been generated, so every record carried all three prompt versions — including
the two that never touched it.

The Prefect pipeline generates per-strategy: each record is produced by exactly one prompt, and the record already carries its own `question_type`. Per record, only one generation prompt version applies. The dict was solving a batch-application problem that no longer exists.

## Options considered
1. Keep `Dict[str, str]` — retains tracer parity, requires the existing JSON serialize/deserialize validator for Parquet round-trip.
2. Flatten to `str` — one prompt version per record, matching how the pipeline actually generates.
3. Flatten to multiple fields (one per question type) — preserves the dict's information but as columns; carries the same irrelevant-fields problem.

## Selected option
Option 2 (flatten to `str`), generalised into the schema-wide rule above.

## Rationale
- Columnar formats reward flat, primitive-typed schemas. Every nested field is a small tax collected on every read and write.
- `generation_prompt_version` was the odd one out: its siblings (`lex_enrich_prompt_version`, `semantic_enrich_prompt_version`) are already flat strings. Flattening restores symmetry — all three prompt-version fields now have the same shape and query the same way.
- The dict's per-record content was mostly noise: an FR question carrying the MCQ prompt filename tells you nothing about that record.

## Trade-offs
**Pros:**
- `deserialize_prompt_version` validator can be deleted.
- Parquet round-trip becomes a plain `string` column — no JSON encode/decode, stable type inference across files.
- Directly queryable (`WHERE generation_prompt_version = ...`) without unpacking.
- Silver-tier deserialization simplifies for the same reason — the custom dtype handling in PyArrow was largely there to accommodate nested fields.

**Cons:**
- If generation ever uses multiple prompts per record (e.g. system + task, or multi-turn), a single field won't hold them — that would need one flat field per prompt role. Judged acceptable: flat fields per role remain clearer than a dict.
- Loses tracer parity; historical tracer data would need transformation to match the new shape.

## Risks
- Existing tracer/Silver data written with the dict shape will not match the new schema. Migration or a compatibility shim may be needed if that data is re-ingested.
- Flattening is applied field-by-field; until the full inventory is catalogued (see below), the schema is mixed.

### Fields affected
- `generation_prompt_version` — `Optional[Dict[str, str]]` → `str`.
- [TBD] a further nested field in the enrichment/validation schemas is suspected to benefit from the same treatment — to be identified and added here.

## Consequences & Future considerations
- ADR left open: additional instances are added to *Fields affected* as they are found, rather than opening a new ADR per field.
- `batch_generation_info` (the pipeline's nested lineage block) is a candidate for the same reasoning — it is a deeply nested dict-of-dicts. Current intent is to lift only the gate-relevant fields (`generation_model`, `generation_prompt_version`) onto the record and leave the remainder in the
  JSONL as pipeline-local observability, rather than carrying the block onto the typed record.
- Related: ADR-P2-023 (DraftQuestion as pipeline-spanning SOT) — the flat-field rule applies to the derived Draft model as well as the gate models.
