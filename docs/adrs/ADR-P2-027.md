# ADR-P2-027: Certified corpus details in question lineage (Question lineage)

**Status:** Accepted (2026-11-27) <br>
**Phase:** 2


## Decision

Every generated question records which certified corpus and which exact chapter text it
was generated from.

ADR-P2-026 made the corpus a trust boundary: preflight verifies at the start of each
generation run that the chapters the run reads are the certified bytes, and the run
manifest records the `corpus_id` and every chapter's sha256. That proves the *run* used
certified text, but a *question* carried no link back to it. Once a question is in Silver,
the append-only system of record, finding its source text meant joining back to a run
manifest and guessing which of the run's chapters went into its call.

Two optional fields are added to `GenPipelineMetadata`:

| Field | Type | Value |
|---|---|---|
| `corpus_id` | `CorpusId \| None` | the certified corpus the run was verified against |
| `source_chapter_sha256` | `dict[str, Sha256Hex] \| None` | the generation call's chapter batch: file name → certified sha256 |

- **Values come from preflight.** In the chapter loop, the call's dict is built from
  `chapter_batch` with a strict lookup (a missing name is a bug and stops the run), carried
  on the call metadata, and stamped on every question from that call.
- **Format vs values.** The model checks format only (`CorpusId`, `Sha256Hex`, shared with
  the corpus record in `core.models`). Preflight checks the values against the certified
  record at generation time.
- **Silver only.** `GenPipelineMetadata` is not projected to Gold, so the runtime dataset is
  unaffected.


## Options considered
1. **Run-level lineage only.** Keep `corpus_id` and chapter hashes in the run manifest, as
   now.
2. **The call's batch.** Stamp each question with every chapter in its generation call
   (`batch_size`, default 2).
3. **The question's own chapter.** Map `source_reference` (the chapter title the LLM picked)
   back to its file name within the call's batch, and stamp that one chapter's hash.

## Selected option
Option 2 (the call's batch)

## Rationale

- **Lineage records facts about the inputs.** The prompt contains every chapter in the
  batch, so the batch is exactly "the text the question was generated from". It is
  verifiable and cannot be wrong.
- **Which chapter is a claim.** `source_reference` is the LLM's pick among the batch's
  titles; nothing verifies it. Option 3 would record that claim as provenance: a question
  attributed to the other valid chapter maps successfully and is silently wrong. Keeping
  the two apart means the claim can later be checked against recorded inputs instead of
  trusted.
- **Self-describing records.** Option 1 leaves the question unable to say where it came
  from on its own, and loses which subset of the run's chapters its call used.
- **Dict, not a single hash.** One entry per source fits today's batches and future
  thematic questions (several excerpts per call) without a schema change.
- **Optional fields.** Follows the schema-evolution rule (Optional → backfill → Required).
  Records written before this ADR read as `None`: lineage unknown.

## Trade-offs
**Pros:**
- Every new question is traceable to the certified bytes it was generated from.
- Validation can reload the exact chapters a question saw and confirm them by hash, giving
  validation the same trust boundary preflight gives generation.
- Impact analysis: if a chapter is corrected and recertified, questions generated from the
  old bytes can be found by hash.
- Simple and exact: no title mapping, no no-match case.
- Additive: existing records and the notebooks that import `core.models` are unaffected
  (checked).

**Cons:**
- Batch-level, not chapter-level: which chapter a question belongs to is still unverified.
- Slightly larger records (one hash per batch chapter on every question; Silver only).

## Risks

- **Misattributed source hint.** `source_reference` drives the runtime source hint, so an
  LLM that names the wrong batch chapter shows the player a wrong hint. Lineage does not
  catch this, but makes a deterministic check possible (see below).
- **Key drift.** The lookup relies on preflight and the chapter loop using the same file
  names (`path.name` from the same `chapter_file_paths`). Mitigated by the strict lookup,
  which fails the run rather than stamping partial lineage.

## Consequences & Future considerations

- **Source attribution check** (pending design change #8): a deterministic check in
  validation that loads the batch chapters through lineage, confirms them by hash, and
  finds which chapter `source_quote` comes from using graded matching (E2, since quotes are
  often spliced). Placement and handling decided after measuring the misattribution rate on
  the first full book run.
- **Validation context through lineage:** the RAG triad loads chapter text via the lineage
  hashes, so validation verifies against the certified bytes.
- **Thematic questions:** `source_reference` becomes `list[str]`, and themes need their own
  certification before the first thematic run. `source_chapter_sha256` already supports
  several sources.
- **Verified:** unit tests (lineage on the DTO and the written record; a malformed hash is
  quarantined) and a trial run (2 chapters, 1 call), where every question carried the
  corpus id and both chapter hashes, matching the run manifest.
