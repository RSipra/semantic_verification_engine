# ADR-P2-017: Serverless Deployment (FastAPI)

**Status:** ✅ Accepted  
**Phase:** Phase 2 (System & Semantic Intelligence)

## Decision

Transition the runtime from a persistent VM to a stateless, serverless container environment. This will move the system design away from infrastructure-heavy management to a cloud-native architecture with automatic scaling and reduced operational burden.

## Options considered
1. **continue with always-on hosting VM**. Requires manual management of the OS, security patches, and firewalls. Incurs costs even when idle and has a fixed performance ceiling with concurrent users.
2. **Serverless container deployment(Google Cloud Run)**: Provides a managed environment that scales to zero when idle and scales up instantly to handle multiple concurrent users.

## Selected option
Option 2 (serverless container deployment)

## Rationale

While Phase 1 proved the game logic on a VM, Phase 2 aims for a more robust, professional architecture. This choice is driven by three key factors:

- **Scalability and concurrency**: Unlike a single-session CLI on a VM, a FastAPI serverless deployment allows the application to handle multiple concurrent users by spinning up additional instances as needed.
- **Operational decoupling**: Moving to serverless removes the VM management overhead (UFW, OS updates, SSH tunnels). This allows the focus to shift entirely to application logic and semantic intelligence.
- **Cost efficiency**: By utilizing a *scale-to-zero* model, the project remains publicly accessible 24/7 runnig within the Google Cloud Run free-tier limits. The game can scale elastically to meet demand while effectively scaling to zero during idle periods. This move eliminates the $4/month Static IP cost and shifts the focus from managing infrastructure to optimizing application logic and semantic intelligence.

### Supporting evidence (measured startup cost, 06-Jul-2026)

The current GoTTY-on-VM deployment spawns a fresh `python main.py` process
*per browser connection*, so full startup re-runs on every connect with no
warm-state persistence. Instrumenting `main.py` (file-based timing, to survive
GoTTY's per-connection PTY routing) on a cold connection measured:

| Phase | Cost |
|---|---|
| Eager ML-stack imports (`game_app` import chain) | **~53s** |
| `orchestrate_application_startup` (SBERT + hydration + validation + LLM) | ~10s |
| Lazy import of `engine.startup` | ~0.85s (no-op; stack already loaded upstream) |
| **Total real startup cost (re-run per connection)** | **~63s** |

(A ~19s gap in the intro was interactive player input, not compute, and is excluded.)

Two findings sharpen the decision:
1. The main delay is **eager ML-stack imports** resolved at the top of the `game_app` import chain; a deferred `engine.startup` import was a no-op (no effect) because the heavy stack was already loaded. This is import-time cost happening before any application logic runs.
2. Under GoTTY this ~63s is paid **on every connection**. A FastAPI single-boot application amortises it to **once per container instance** at startup, after which all requests reuse the warm in-memory state, directly eliminating the per connection re-execution.
3. Resource profiling during a cold start shows the ~53s import phase is **disk-I/O bound, not memory or CPU**: MEM peaked at ~46% (435/954 MiB), CPU stayed at 20–37%, while BLOCK_IO climbed ~600MB —> indicating slow disk reads loading the ML stack (torch/transformers/sentence-transformers) on the constrained e2-micro. This does not reproduce on local hardware.

This surfaces a trade-off between two Cloud Run configurations, and the  choice is **traffic-dependent**:

- **Scale-to-zero (default, low traffic):** zero idle cost, at the price of a
  first-user cold start after idle. Optimal when usage is sparse (e.g. a handful of users every few days). An always-on instance would sit idle most of the time and the interim UX startup notice (or a richer themed intro) absorbs the occasional cold start acceptably.
- **Minimum instances (`min-instances=1`, higher traffic):** keeps one container warm so no user hits a cold boot, justified once traffic is steady enough that it noticeably improves UX at scale to justify the cost of the always-on instance.

**Policy:** default to scale-to-zero; promote to `min-instances=1` when observed traffic crosses a sustained-usage threshold (to be determined based on usage patterns). The switch is a one-line Cloud Run config change, so the decision stays cheaply reversible and can track actual demand.

## Trade-offs

**Pros:**
- Zero idle cost. No billing for time when the game is not being played.
- Infrastructure abstraction. No server maintenance, OS patching, or manual firewall (UFW) management.
- Elastic scale. Automatically handles traffic spikes without manual intervention.
- Improved security. Ephemeral containers provide a reduced attack surface compared to a persistent VM.

**Cons:**
- Cold start latency on first request
- Statelessness requirement. The game can not rely on local memory to keep track of players; state must be managed via API requests or external storage.
- Less control over underlying infrastructure

## Risks
- Cold start UX. Latency might make the first interaction feel slow to a new user.
- Resource constraints. Heavy NLP models or long-running logic must be optimized to fit within the serverless memory and timeout limits.

## Consequences & Future considerations
- Architecture shift. The game logic must be refactored into a stateless FastAPI wrapper.
- State management. Scores and session data will be handled via client-side tokens or a lightweight database rather than persistent VM memory.
- Deployment pipeline. The in-situ VM build will be replaced by a modern CI/CD flow where images are pushed to a registry (e.g., Artifact Registry) and deployed automatically.
- AI/SLM integration. Any Small Language Models (SLMs) used for semantic checking must be lightweight enough to load quickly during container startup and execute within request timeouts.
- Warm vs. cold configuration. A decision is required between scale-to-zero (zero idle cost, first-user cold start) and min-instances=1 (always warm, small idle cost). Deferred pending the FastAPI migration and measured post-optimization cold-boot time.
- Import optimization. Startup is slow because the container reads large ML libraries off slow disk on every load. The FastAPI restructure should:
    1. defer and trim eager ML-stack imports in the `game_app` chain so less is read and only when needed,
    2. benefit from Cloud Run's faster instance storage plus single-boot amortisation (loaded once per instance, not per connection). Adding container memory is not the lever: the bottleneck is disk I/O, not RAM.
